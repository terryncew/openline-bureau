# OpenLine limited public beta assignment

This assignment updates the original Bureau Select brief. The product is a
small OpenLine contribution and discovery workflow built on Bureau, Exchange
and Wallet. **Bureau Select remains the buyer comparison feature inside that
workflow.** Publication requires a separate owner decision; this branch does
not open the beta to the public.

The intended first users are people and independent AI developers who can
publish a useful capability, describe its terms, contribute evidence, evaluate
someone else's work, and receive a genuine inquiry. A synthetic catalog alone
does not establish that these people exist or that this workflow is useful.

## Smallest complete workflow

1. A contributor proposes a versioned capability as reviewed GitHub data.
   Identity, source provenance, usage terms, attribution and publication
   permission accompany its supporting evidence.
2. A different contributor proposes an evaluation bound to that exact version.
   Test conditions, evaluator identity, conflicts, failures, limitations and
   missing outcomes are part of the record, even when the result is unfavorable.
3. Bureau compiles validated public data and receipt assessments. It preserves
   source hashes, reports unsupported formats, distinguishes signature checking
   from observed task success, and exposes incomplete evidence.
4. Exchange serves a searchable catalog, version history, evidence detail,
   comparison and a stable JSON discovery interface. Workers and reusable
   skills remain distinct.
5. Bureau Select helps a buyer compare relevant candidates by task, disclosed
   price, conditions and evidence. Selection is advice. It grants no authority
   and makes no promise about future performance.
6. The buyer deliberately creates a public GitHub work inquiry or purchase
   request. It is a real request for human follow-up, with no automated payment,
   acceptance, commissioning or execution.
7. Improvements point to earlier capability versions and retain attribution and
   evidence history. Attribution and licensing metadata do not establish legal
   ownership, clear third-party rights, or enforce a license.

## Evidence language

Use specific dimensions instead of a universal score:

| Display | Meaning and limit |
| --- | --- |
| Structurally supported receipt | Recognized data with the required fields; this alone proves no signer identity or outcome. |
| Cryptographic authenticity | Signature checking against the relevant explicit key policy; a valid signature authenticates signed bytes, not correctness, completeness, identity outside that policy, or economic value. |
| Self-reported | The publisher's claim; it has not become an independently verified result merely by being reviewed for publication. |
| Independently reported | A separate reviewed contributor reports the exact version, procedure, conditions and results; the report has not yet been reproduced by a separate maintainer. Different accounts do not establish organizational independence. |
| Independently reproduced | A separate maintainer's reviewed reproduction binds the exact evaluation, sample and case outcomes. Confidence remains bounded by that method, environment and declared independence. |
| Simulated / synthetic | Fixture inputs, outputs, actors or currency. They are never represented as real contributors, work, or payment. |
| Unknown / missing | The available records do not establish the fact. An omission is not a zero, a success, or proof that an event did not happen. |

Signed buyer acceptance, reproducible task success, a receiver's executed effect
and actual payment are separate facts. The beta must not collapse them into a
single "verified" badge. A reviewed contribution is eligible for publication;
it is not certified safe, truthful or successful.

## Existing foundations stay intact

- Bureau remains the evidence and allocation engine. Its public receipt
  adapters, metrics and private sharing rules keep their existing meanings.
- Exchange is extended with a public catalog and request workflow. The existing
  offer and transaction protocols are preserved.
- Wallet supplies existing authority and signature concepts. Evidence
  verification does not authorize a consequence; the owner and receiving Gate
  retain that boundary. The beta does not execute the Wallet buyer flow.
- Existing protocols, recorded artifacts, frozen experiment definitions and
  published findings are unchanged. New public records require new reviewed
  versions rather than editing frozen evidence to improve a story.

The original [BUREAU-ALLOCATION-001](../../BUREAU_ALLOCATION_001.md) remains a
synthetic economic comparator. It uses matched tasks and equal budgets, freezes
recommendations before held-out outcomes, and compares Bureau to the ordinary
cheapest eligible offer baseline. Its negative results must remain visible:
the mixed case improved completion but reduced accepted work per settled
simulated dollar and chose worse on a task; reversal lost all four choices;
sparse evidence was inconclusive. None establishes commercial advantage.

## Explicit boundaries

No new accounts, billing, token economy, paid APIs, hosted autonomous workers,
server execution of contributor code, or real-payment implementation are needed
for this beta. Contributed code is a link or data describing a capability; the
site never downloads or executes it. Real customer inputs and private evidence
are outside the authorized task. Public synthetic examples are a separate,
prominently labeled learning mode; an empty reviewed public catalog is honest.

Implementation uses isolated feature branches. Draft PRs, local screenshots,
instructions and a deployment plan are authorized. Public deployment, merging,
initiating payments, accepting customer data and paid API use each require
separate approval.

## Release acceptance

The code review must demonstrate the full contribution → separate evaluation
→ Bureau validation → Exchange discovery/comparison → deliberate request path.
Automated validation must reject malformed data, unsafe URLs, traversal and
oversized inputs, unsupported verification claims, stale review bindings and
unauthorized/private publication. Browser tests must cover real and synthetic
mode separation, comparison, evidence detail, machine discovery and request
generation.

There must be usable contribution instructions, versioned JSON schemas, clear
moderation and privacy rules, screenshots, passing reproducible tests and draft
PRs. Opening to outsiders additionally requires every condition in
[DEPLOYMENT.md](DEPLOYMENT.md), including approved operating owners and at least
one permissioned real capability with a separately contributed evaluation.
Technical completion by itself is not evidence of adoption, an economically
useful allocation policy, production identity, or a mature marketplace.
